## 1. 2025년 12월이 분기점

카파시가 가장 먼저 짚는 건 시점이다. **에이전트가 진짜로 작동하기 시작한 건 2025년 12월부터**.

본인도 1년 가까이 Claude Code 같은 도구를 써왔는데, 그 1년 동안은 "코드 덩어리를 던져 주면 가끔 맞고 가끔 직접 고쳐야 하는 수준"이었다. 12월에 휴가가 생겨서 시간이 났고, 최신 모델로 다시 돌려봤더니 그냥 코드가 나오더라는 것.

흥미로운 건 이걸 <mark>곡선이 아니라 계단</mark>으로 본다는 점이다. 점진적으로 좋아진 게 아니라 어느 시점에 끊어진 분기점.

리서치 → 계획 → 코드 작성 → 테스트 → 디버깅까지 한 흐름으로 끝까지 가는 게 가능해진 시점. 만약 작년 가을쯤 "AI 코딩 별로던데"라고 결론 내렸다면, **그 시점에서는 맞는 결론이었고 지금은 다시 해봐야 한다**.

## 2. Software 1.0 / 2.0 / 3.0 

카파시가 자주 쓰는 프레임. 소프트웨어를 세 단계로 나눈다.

| 단계 | 무엇이 프로그램인가 |
|---|---|
| 1.0 | 우리가 직접 코드를 짠다 |
| 2.0 | 신경망을 학습시킨다 (가중치가 코드를 대체) |
| 3.0 | 프롬프트가 곧 프로그래밍 (컨텍스트 윈도우가 레버) |

{{< note1 >}}
### 사례 ① — 오픈클로 설치
- **1.0** : OS별·환경별 분기 처리가 들어간 수백 줄짜리 bash 스크립트.
- **3.0** : 텍스트 한 덩어리(스킬 하나)를 에이전트에 넘기면 끝. **에이전트의 지능이 분기 처리를 대신**한다.
{{< /note1 >}}

{{< note1 >}}
### 사례 ② — 메뉴젠
식당 메뉴판에 사진이 없을 때, 메뉴 텍스트별로 음식 사진을 생성해주는 앱을 카파시가 만들었다.
- **1.0/2.0** : 사진 업로드 → OCR → 이미지 생성 API 반복 호출 → 렌더링 → 배포. 백엔드와 프론트엔드, Vercel 배포까지 필요한 진짜 앱.
- **3.0** : 메뉴 사진을 Gemini(nano banana)에게 주고 *"메뉴 위에 음식 사진을 오버레이해줘"* 한 줄. **앱이 불필요해졌다.**
{{< /note1 >}}


{{< fold "고찰" >}}
여기서 드는 개인적인 생각은 그래서 내가 나아가야할 방향은 뭔데? 중간 단계를 어떻게 인식해볼 수 있지? 였다.
클로드에게 물어보니 아래와 같이 답했다.

{{< note3 >}}
  - 본질만 남기고 형식은 신경망에 맡기는 습관 — "이 단계 꼭 내가 만들어야 해?" 한 번 더 묻는 것.
  - 모델이 아직 못 하는 영역으로 시간을 쓴다 — 도메인 지식, 시스템 설계, 취향·판단.
  - 새로운 길(new things available)을 의식적으로 찾는다 — 1.0 시대엔 불가능했던 것이 지금 가능한 게 뭔지. 카파시의 LM 위키, 메뉴젠이 그 예. 
{{< /note3 >}}

그럼 내가 할 수 있는 일이 사라지는건 아닐까? 이 내용에 대해서도 클로드와 함께 고찰해봤다.

{{< note3 >}}
| 이유 | 설명 |
|---|---|
| 데이터 형태가 다름 | 수요예측·이상탐지는 시계열 수치, 추천은 user×item 상호작용 행렬. LLM이 잘 다루는 텍스트가 아님 |
| 정확도 | tabular 데이터에선 여전히 XGBoost/LightGBM이 LLM을 이김. 이건 한동안 안 뒤집힘 |
| 비용·지연 | 추천은 ms 단위 응답이 필요. LLM 호출은 초 단위 + 토큰당 과금. 경제성이 안 맞음 |
| 검증 가능성이 오히려 강점 | MAPE, RMSE, Recall@K — 채점이 명확하니까 특화 모델이 RL로 더 잘 학습됨 |
{{< /note3 >}}

{{< note3 >}}
  | 줄어드는 일 | 늘어나는 일 |
  |---|---|
  | Feature engineering 노가다 | 문제 정의 — "예측해서 뭘 할 건가" |
  | 보일러플레이트 (전처리, 시각화, 베이스라인 모델) | 평가 설계 — 비즈니스 지표와 모델 지표 연결 |
  | Hyperparameter tuning 수동 | 시스템 설계 — 추천 결과를 어디에 어떻게 노출할지 |
  | 단순 분류/NER을 위한 작은 모델 학습 | LLM과 특화 모델을 언제 섞을지 판단 |
  | EDA 노가다 (집계, 분포, 결측) | 이해(understanding) — 데이터 뒤의 사용자/사업 모델 |
{{< /note3 >}}

이것만 보면 오히려 일하기가 더 수월해질 수 있겠다. 물론 이미 많이 수월해졌지만.. <br>
그래도 마지막 병목은 똑같다. "왜 이걸 예측하는가, 어떻게 검증할 것인가." <br> 
AutoML이 하이퍼파라미터는 돌려줘도, 문제를 잘못 정의했다는 건 내가 알아채야한다. 

결국 모델 만드는 노동은 줄지만, 모델로 뭘 풀지 정의하는 일은 오히려 더 중요해진다. 본질이 모델을 만드는 데서 문제 정의·의사결정 설계자로 이동하고 있다
{{< /fold >}}

## 3. AI는 채점 가능한 영역에서만 천재다

김플립 영상에서는 이게 인터뷰에서 가장 실용적인 프레임이라고 생각한다고 말한다.

{{< note2 >}}
전통적 컴퓨터는 **코드로 명시할 수 있는 것**을 자동화한다. <br>
이번 라운드의 LLM은 **검증할 수 있는 것**을 자동화한다.
{{< /note2 >}}

<mark>답이 맞는지 채점할 수 있는 영역(수학, 코드 컴파일/테스트 통과)에서는 RL로 쭉쭉 강해진다.</mark> 그렇지 않은 영역은 들쭉날쭉(jagged) 하다.

예로 황당한 사례 두개를 보여준다. 
- **스트로베리 R** : `strawberry`에 R이 몇 개냐고 물으면 한동안 `2`라고 답하던 시절이 있었다. 글자 수 세기를 못 했다.
- **세차장** : *"세차장이 50m 앞인데 차로 갈까 걸어갈까?"* 물으면 가까우니까 걸어가라고 답한다. 차를 세차하러 가는 건데.

10만 줄 코드베이스를 리팩토링하고 제로데이 취약점을 찾아내는 모델이, 세차장에는 차로 가야 한다는 걸 모른다. <br>
이게 jagged intelligence의 실체다. 한쪽영역에서는 천재 수준이지만 일상적 상식은 무너지기도 한다. 

그래서 카파시 결론은 — **이 들쭉날쭉함이 남아 있는 한, 인간이 루프 안에 있어야 한다.** <mark>LLM을 *도구*로 다뤄야지 결정권을 넘기면 안 된다</mark> 라는 것이다.

## 4. 바이브 코딩 vs 에이전틱 엔지니어링

본인이 만든 두 용어의 차이를 카파시가 가장 깔끔하게 정의한다.

| | 바이브 코딩 | 에이전틱 엔지니어링 |
|---|---|---|
| 무엇을 하는가 | **바닥을 올린다** (raising the floor) | **천장을 지킨다** (preserving the quality bar) |
| 대상 | 모두 (비개발자 포함) | 프로페셔널 소프트웨어 |
| 핵심 | 누구나 앱을 만들 수 있게 | 기존 품질 기준 유지하면서 더 빠르게 |

핵심은 *상호 보완적*이라는 것. 바이브 코딩이 멋진 건 인정하지만, **바이브 코딩했다고 보안 취약점을 도입해도 된다는 뜻이 아니다.** 책임은 여전히 본인한테 있다. <br>
그리고 카파시는 *"10배 엔지니어"* 라는 옛 표현이 이제 부족하다고 본다. <mark>에이전트를 잘 다루는 사람은 **100배, 1000배까지도 가능한 시대**</mark>라고.

## 5. AI-Native한 사람

같은 도구를 써도 결과물이 5배, 10배 차이가 난다. 카파시는 그 차이를 이렇게 정리한다.

| 구분 | Mediocre | Fully AI-Native |
|---|---|---|
| **도구 활용** | 한두 개 도구만 익숙하게 쓴다 | 가능한 모든 도구를 끌어쓴다 |
| **기능 활용** | 기본 기능만 쓴다 | 그 도구의 모든 기능을 파고든다 |
| **자기 셋업** | 회사가 깔아준 거 그대로 | 자기 워크플로우·셋업에 투자한다 |
| **채용** | "코딩 잘하는 사람"을 뽑는다 | **agentic engineer**를 적극 채용한다 |

어떤 사람은 채팅창에 한 번에 한 줄씩 시키고, 어떤 사람은 **MCP 서버 붙이고, 스킬 만들고, 슬래시 커맨드 등록하고, 후크 쓰고** — 이게 새로운 격차가 되고 있다. <br>

이걸 보면서 내 현재 상태를 진단하게 됐다. <br>
과연 지금 나는 Fully AI-Native한 사람인가? 그래서 클로드한테 내가 널 얼마나 잘 활용하고 있는지를 물어봤다. <br>
이거에 대한 이야기는 또 다른 글로 써보려고 한다. 다들 한번 물어보길.

## 6. 그래서 인간은 뭘 더 잘해야 하는가

에이전트는 놀랍지만 **인턴 수준**이다. 지치지 않고 빠른 인턴.
그래서 인간한테 남는 영역이 명확해진다.

- **미학(taste)** — 이게 좋아 보이는가, 나빠 보이는가
- **판단(judgement)** — 이게 옳은 결정인가
- **사양(spec)** — 어떤 게 더 우아한가, 어떤 구조여야 하는가
- **감독(oversight)** — 얘가 지금 헛소리하고 있는 건 아닌가

{{< note1 >}}

**카파시의 사례 — 메뉴젠 결제 이메일** <br>

메뉴젠에 구글 로그인 + Stripe 결제를 붙였더니, 에이전트가 **Stripe 이메일과 구글 이메일을 매칭해서 크레딧을 배정**했다. 고유한 유저 ID를 안 만들고. <br>
두 서비스에 다른 이메일을 쓰는 사람은 결제했는데 크레딧이 매칭이 안 되고, 보안상으로도 위험하다. 누군가 다른 사람 이메일로 Stripe 결제하면 그 사람 계정에 크레딧이 들어가버린다. <br>

<mark>사람은 "잠깐, 유저 ID는 고유해야 하고 모든 걸 거기 묶어야지"를 1초 만에 결정하는데, 에이전트는 그걸 못 한다.</mark> <br>
**인간이 스펙을 잡고, 에이전트가 디테일을 채운다.** 이게 처방이다.
{{< /note1 >}}

### 디테일은 버리고, fundamentals는 지킨다

{{< note2 >}}
*"PyTorch의 `dim`이냐 `axis`냐 — 나는 더 이상 기억하지 않는다. 그건 인턴의 일이다."* — Karpathy
{{< /note2 >}}

정리하면 이렇게 나뉜다.

| ✅ 지킬 것 (KEEP) | ❌ 버려도 될 것 (DROP) |
|---|---|
| 개념적 이해 | API 디테일 / syntax |
| 큰 그림 · 아키텍처 감각 | 라이브러리 함수명 암기 |
| Spec 설계 능력 | 직접 타이핑하는 속도 |
| Taste · Judgment | 매번 구현 코드 외우기 |

- **구현 → 설계로 무게중심이 옮겨간다.**
  
이게 카파시가 말한 ***"새로운 스킬셋"*** 의 정체다. <mark>코드를 쓰는 사람에서 시스템을 설계하고 에이전트를 매니징하는 사람으로의 이동.</mark>

## 7. 에이전트 네이티브 세계

에이전트 네이티브는 두가지 측면이 있는걸로 보인다.

| 측면 | 누가 책임 | 무엇을 한다 |
|---|---|---|
| A. 사용자 측 (Consumer-side) | 본인 | 본인이 반복하는 CLI·설치·git 작업을 에이전트에게 위임. 반복되면 Skill·Hook으로 박음 |
| B. 공급자 측 (Provider-side) | 도구·서비스 회사 | docs·설치·API·배포를 *에이전트가 흡수 가능한 형태*로 제공 |


그리고 한 단계 더 나가면 — **에이전트끼리 커뮤니케이션하는 세계**. <br>
*"제 에이전트가 당신 에이전트랑 미팅 디테일 잡게 하겠습니다."* 캘린더 조율, 자료 조사, 협상까지 에이전트끼리 처리되고 우리는 결과만 받는 그림.

## 8. 마지막 한 줄 — 외주가 가능한 것과 불가능한 것

인터뷰 마지막 질문이 *"인텔리전스가 이렇게 싸지는 시대에, 인간이 끝까지 직접 해야 하는 건 뭐냐?"* 였다.

카파시가 인용한 트윗 한 줄이 인터뷰 전체를 관통한다.

{{< note2 >}}
**You can outsource your thinking, but you can't outsource your understanding.** <br>
사고는 외주를 줄 수 있어도, 이해는 외주를 줄 수 없다.
{{< /note2 >}}

- **사고(thinking)** 는 일종의 처리 작업이다. 정보 받고, 분석하고, 단계 밟아서 결론에 도달하는 것 — LLM이 잘한다. 
- **이해(understanding)** 는 다르다. 정보가 자기 뇌에 들어와서, 자기 모델 안에서 자리 잡고, 다른 정보랑 연결되고, *"아, 이게 이런 거였구나"* 라는 깨달음으로 변환되는 것. 이건 본인이 직접 해야 한다.

코드 속도, 빌드 속도는 더 이상 병목이 아니다. **뭘 만들지, 왜 가치가 있는지, 에이전트를 어떻게 지휘할지** — 이게 마지막 병목이고, 외주가 안 된다. <br>
<mark>이해를 외주 주지 마라. 코드를 칠 줄 아는가는 별로 안 중요하다. 왜 이걸 만드는가, 어떻게 검증할 것인가는 본인이 해야 한다.</mark>

---

{{< note4 >}}
카파시 본인이 *"뒤쳐졌다"* 고 느낀다고 했다.<br>
그 말은 우리가 끝났다는 뜻이 아니라 **모두가 같은 출발 선상에 섰다**는 뜻에 가깝다. <br>
지금부터 키워야 할 근육은 빠른 타이핑이 아니라 취향, 판단, 그리고 이해. 이건 결국 직접 써보고 결정 내려보고 틀려보면서 쌓이는 것 같다.
{{< /note4 >}}
