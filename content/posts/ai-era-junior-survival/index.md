최근에 [AI is Making Junior Devs Useless](https://beabetterdev.com/2026/03/01/ai-is-making-junior-devs-useless/) 라는 글을 읽었다. <br>
이제 주니어는 아니지만 주니어의 마음으로 혼자 위키에 끄적여뒀던 메모를 한 번 정리해보려고 한다.

요지를 한 줄로 줄이면 이렇다.

{{< note2 >}}
**AI는 실행을 평준화시켰다. 그래서 이제 희소한 건 "판단"이다.**
{{< /note2 >}}

코드를 짤 수 있느냐는 더 이상 변별력이 아니다. <br>
**그 코드가 왜 그렇게 짜였는지 설명할 수 있느냐**가 사람과 사람 사이의 차이를 만든다.

---

## 시니어의 가치는 어디서 오는가

원문에서 가장 인상적이었던 표현은 **"실패 패턴 인식 (failure pattern recognition)"** 이다.

시니어 개발자가 가진 진짜 자산은 빠르게 코드를 짠다는 사실이 아니다. <br>
<mark>새벽 두 시에 장애 대응을 해본 경험, 설계 실수로 인한 데이터 유실, 디버깅을 며칠씩 끌어본 시간들 — **이 모든 게 몸으로 학습된 직관**이다.

문제는 AI가 이 학습 과정을 통째로 건너뛰게 만든다는 것. <br>
주니어는 코드는 짤 수 있는데, **그 코드가 왜 그래야 하는지에 대한 감각이 비어있다.** 이게 원문에서 말하는 *얕은 역량 (shallow competence)* 이다.

코드 리뷰에서 "왜 이 라이브러리를 쓰셨어요?"라고 물었을 때 "AI가 추천했어서요"가 답이라면, 그건 사람이 아니라 단순 통로일 뿐이다.

---

## 그래서 어떻게 해야 하는가 — 5가지 전략

원문의 다섯 가지를 옮기되, 내가 데이터 분석/AI 일을 하면서 와닿았던 예시들을 같이 붙여본다.

### 1. 기초를 제대로 학습할 것

좋은 코드가 무엇인지 알아야 AI 결과물을 **평가**할 수 있다. AI는 잘못된 코드도 자신만만하게 뱉는다. 평가 기준이 내 머릿속에 없으면 그냥 받아 적게 된다.

{{< note1 >}}
원문이 권장한 책 두 권:

- *Head First Design Patterns* — 코딩 패턴과 그 패턴을 왜 쓰는지
- *Designing Data-Intensive Applications* — 데이터 집약 시스템의 설계 원리 (저자 표현으로 "어렵게 배워야 할 것들을 미리 알려주는 책")
{{< /note1 >}}

분야가 다르더라도 비슷한 원칙은 똑같다. **AI 없이도 한 번은 직접 굴러본 영역**이 자기 안에 있어야 한다.

### 2. 장애 사례를 공부할 것

Cloudflare, AWS, Azure, Google이 큰 장애 후에 공개하는 **포스트모템 (post-mortem)** 문서들이 있다.

처음 읽으면 "이게 왜 흥미롭지" 싶은데, 몇 개 읽다 보면 **남이 비싼 값에 산 교훈을 공짜로 얻는** 셈이라는 게 보인다. <br>
"이런 조합이 이런 식으로 터지는구나" 같은 패턴 인식이 쌓인다. AI는 절대 가르쳐주지 않는 종류의 지식이다.

### 3. 고군분투를 의도적으로 만들 것

이게 5개 중 가장 어려운 거 같다. <br>
에러가 나면 반사적으로 AI에 붙여넣게 된다. 
하지만 **스스로 해답을 찾는 과정을 겪어야한다.** : 스택 트레이스를 읽고, 코드를 추적하고, 로그를 확인하고, 무엇이 잘못되었는지 가설을 세워볼 것

{{< note1 >}}
**스택 트레이스 읽는 법** — 맨 아래 줄(실제 에러)부터 위로

```sh
Traceback (most recent call last):
  File "main.py", line 42, in run_pipeline
    result = process_data(df)
  File "utils.py", line 17, in process_data
    return df["searchQuery"].apply(clean)
KeyError: 'searchQuery'
```

- **어떤 에러인지** → `KeyError: 'searchQuery'` (이 컬럼이 없다)
- **어디서 터졌는지** → `utils.py` 17번째 줄
- **어떻게 거기까지 왔는지** → `main.py` 42번 → `utils.py` 17번 순서로 호출
{{< /note1 >}}

AI에게 던지기 전에 이 정도 추적은 직접 해보자. **로그 한 줄, 가설 하나, 검증 한 번.** <br>
이 사이클이 쌓여야 다음 번에 비슷한 에러를 5초 만에 알아본다.

### 4. 이해하지 못한 코드를 절대 출시하지 말 것

원문에서 가장 강하게 말한 부분이다. <br>
커밋하는 모든 라인에 대해 **"왜 이 라이브러리인지, 왜 이 패턴인지, 트레이드오프가 무엇인지"** 를 본인이 설명할 수 있어야 한다.

트레이드오프란 결국 **무엇을 얻고 무엇을 포기하는가**의 문제다. 속도, 복잡도, 유지보수성, 확장성 같은 축이 매번 충돌한다. 실제 예시 몇 개를 들어보면:

{{< fold "예시 1 — 라이브러리 선택 : Pandas vs Polars" >}}
- **Pandas** : 레퍼런스 많고 디버깅 쉬움. 메모리 많이 먹음
- **Polars** : 빠르고 메모리 효율적. 레퍼런스 적음

→ 데이터가 작으면 Pandas, 크면 Polars
{{< /fold >}}

{{< fold "예시 2 — Airflow DAG 설계" >}}
- **하나의 큰 task** : 코드 짧고 오버헤드 적음. 그러나 중간 실패 시 처음부터 재실행, 어디서 죽었는지 파악 어려움
- **잘게 쪼갠 task** : 실패 지점 정확히 알 수 있고 부분 재실행 가능. 그러나 복잡해지고 task 간 데이터 전달 신경 써야 함
{{< /fold >}}

{{< fold "예시 3 — 패턴 선택 : 하드코딩 vs 환경변수 config" >}}
- **하드코딩** : 지금 당장은 빠름. 추후 값 바꿀 때 코드 전체를 뒤져야 함
- **config 분리** : 유지보수 쉬움. 초기에 구조 잡는 데 시간 듦
{{< /fold >}}

세 가지 다 답이 정해진 게 아니다. <br>
**상황에 따라 어떤 축을 우선시할지를 본인이 골랐다는 사실**이 중요하다. AI가 골라준 거면, 적어도 골라준 이유를 따라가서 내 것으로 만들어야 한다.

속도가 줄더라도 이해가 선행되어야 한다. 

### 5. 답이 아닌 "왜"를 프롬프트로 할 것

마지막으로, AI를 쓰는 방식 자체를 바꾸자.

| 보통 프롬프트 | 더 나은 프롬프트 |
|---|---|
| "이 문제 풀어줘" | "이 문제에 대한 **접근법 3가지**와 각각의 **trade-off**를 설명해줘" |
| "왜 안 돼?" | "이 코드가 실패할 수 있는 시나리오를 추론해줘" |
| "이 라이브러리 코드 짜줘" | "이 작업에 어울리는 라이브러리 후보 3개와 선택 기준을 알려줘" |

전자는 답을 받는 것, 후자는 **사고 과정을 같이 얻는 것**이다. <br>
부수적으로 후자 쪽이 AI의 응답 품질도 더 좋다. (단답형으로 시키는 것보다 비교해보라고 시키면 더 신중해진다.)

---

## 정리
- 코드 작성 속도보다 실패를 통해 축적한 실패 패턴 인식이 중요
- AI를 사용하더라도 에러를 직접 분석하고, 코드를 추적하고, 가설을 세우는 의도적 고군분투 과정이 필수적임
- 커밋하는 모든 코드에 대해 라이브러리 선택 이유, 패턴, 트레이드오프를 직접 설명할 수 있어야 함
