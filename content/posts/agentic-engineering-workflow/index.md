근데 그래서 일이 더 쉬워졌냐? 하면 맞다. 예전엔 눈앞이 캄캄하던 일들도 이젠 문제 없다. <br>
하지만 만능은 아니다. 에이전트가 시키는 일을 잘 못하면 결국 디버깅 시간만 늘어난다. 그래서 새로 필요해진 게 바로 **에이전틱 엔지니어링 (Agentic Engineering)** 이다.

## Part 1. 에이전틱 엔지니어링 9가지 스킬

먼저 한눈에 정리하면 이렇다.

| # | 스킬 | 한 줄 요약 |
|---|---|---|
| 1 | **분해 능력** | 모호한 요구를 에이전트가 한 턴에 끝낼 단위로 잘라준다 |
| 2 | **컨텍스트 설계** | 코드 구조 자체가 에이전트의 시야를 결정한다 |
| 3 | **완료 정의** | "완료"의 기준을 명시 안 하면 stub로 끝난다 |
| 4 | **실패 복구** | 같은 프롬프트로 재시도 X. 실패 유형부터 분류 |
| 5 | **관찰 가능성** | 에이전트가 어디서 길을 잃는지 빨리 캐치 |
| 6 | **메모리 설계** | 세션 간 맥락 복원 시간을 15분 → 5초로 |
| 7 | **병렬 관리** | 여러 에이전트를 동시에 — CTO의 스쿼드 관리와 같은 일 |
| 8 | **추상화 계층** | 반복되는 지시를 스킬로 — 매번 계층이 올라간다 |
| 9 | **감각** | AI는 80%까지. 나머지 20%가 인간의 영역 |

이 중 몇 개만 좀 더 풀어보려고 한다. 

### ① 분해 능력

"이거 만들어줘" 처럼 한 줄로 던지는 게 가장 흔한 함정이다. <br>
에이전트는 모호함을 그대로 받아서 자기 식대로 가정을 채우며 일을 진행한다. 그리고 결과물이 내가 원한 것과 다르다는 걸 나중에야 알게 된다. 그제야 수정 루프 시작.

그래서 본격적인 일을 시키기 **전에** 세 단계를 거치는 게 좋다.

1. **AI와 소크라틱 대화** — 에이전트에게 일을 시키기 전에, 거꾸로 **에이전트가 나한테 질문하게** 만든다. 생각을 캐내는 인터뷰어로 대화하며 질문을 통해 생각을 구조화한다. 
2. **엣지 케이스 사전 정리** — 1단계에서 나온 요구사항을 바탕으로, 모호한 부분을 제거하거나 구체화 시킨다. 또한 예외 상황을 미리 뽑아둔다. <br>
3. **수정 2~3턴으로 축소** — 앞서 대화한 내용을 기반으로 초안 작성 후 2\~3차 수정 과정으로 마무리한다. <br>


{{< note2 >}}
그럼 *"유저 이탈 분석 대시보드를 만들어달라"* 는 task가 떨어졌다고 가정해보겠다. 


📍 **Before — 한 줄짜리 위임**
```
유저 이탈 분석 대시보드 만들어줘.
```

- 에이전트는 "이탈"의 정의를 자기 식대로 추측한다 (예: 30일 무접속)
- 막상 결과물을 보면 내가 원한 게 아니다. **반나절짜리 수정 루프** 시작.

📍 **After — 3단계로 분해**

같은 작업을 다음 세 프롬프트로 쪼개면 결과가 완전히 달라진다.

{{< note1 >}}

**1) 소크라틱 대화 — AI를 인터뷰어로**

```
유저 이탈 분석 대시보드를 만들고 싶어.
본격 구현 전에 네가 인터뷰어가 되어서 내 요구사항을 명확하게 만들어줘.
한 번에 다 묻지 말고, 가장 핵심적인 질문 5개부터 던져줘.

각 질문은:
 - 모호한 부분을 짚는 질문일 것
 - 내가 답을 선택하면 그에 따라 구현 방향이 달라지는 질문일 것
```

- 에이전트가 질문: *"'이탈'을 어떻게 정의하시겠어요? (a) 30일 무접속 (b) 결제 중단 (c) 특정 이벤트 미발생 …"* 

{{< /note1 >}}

{{< note1 >}}
**2) 엣지 케이스 사전 정리**

```
1번 대화로 정리한 요구사항을 바탕으로,
구현 시 마주칠 수 있는 엣지 케이스를 10개 뽑아줘.
각 케이스에 대해:
 - 어떻게 처리할 것인지 너의 제안
 - 내 결정이 필요한 부분은 ★ 표시
```

- 신규 가입 후 1일 이내 이탈한 유저, 결제 환불 후 재가입, 비활성이지만 푸시 알림만 받는 유저… <br>

{{< /note1 >}}

{{< note1 >}}
**3) 스펙 초안 → 2~3턴 수정**

```
앞서 정리한 요구사항과 엣지 케이스를 종합해서 spec.md를 작성해줘.
 - 데이터 소스, 지표 정의, 차트 구성, 필터를 명확히
 - 아직 구현하지 마. 내가 검토 후 수정 요청할게
```

- 초안 받고 → 메모 달아서 수정 → 한 번 더 → 완성.  **이제야 구현 시작.**
{{< /note2 >}}

세 단계가 길어 보이지만 실제로는 **15~20분이면 끝난다.** 이 15분이 반나절 수정 루프를 막아준다. <br>

{{< /note1 >}}

### ③ 완료 정의

가장 무서운 건 에이전트가 "완료했습니다" 하고 보고하는데, 막상 열어보니 **함수 본문이 전부 `return nil` 스텁**이었다는 경우. 원문에서 실제로 겪은 일이다.

해법은 **DoD (Definition of Done) 를 명시적으로 박는 것**. 체크리스트, 중간 체크포인트(1단계 끝나면 보고), "기존 테스트 수정 금지, 새 테스트만 추가" 같은 규칙을 처음부터 박아둔다.

| 위치 | 언제 쓰나 |
|---|---|
| **프롬프트에 직접** | 단발성 task. 빠르게 쓰고 버리는 용도 |
| **`plan.md` / `spec.md` 안에** | 본격적인 작업의 계획 문서 안에 task별로 박아둠 |
| **`CLAUDE.md` (전역 또는 프로젝트)** | 모든 task에 공통으로 적용되는 기준 (예: "테스트 작성 필수", "타입 체크 통과 필수") |

특히 세 번째가 강력하다. `CLAUDE.md` 에 한 번 박아두면 매 프롬프트마다 다시 안 써도 에이전트가 알아서 따라준다. 단발성 작업이면 그냥 프롬프트에 한 줄 추가하면 되고.
    
    근데 사실 클로드가 문서를 무시하는 경우도 있어서 나같은 경우, 정말 중요한 케이스들은 hooks로 설정해뒀다. 

### ④ 실패 복구 

에이전트가 길을 잃었을 때 "다시 해봐" 가 가장 흔한 안티패턴이다. <br>
원문은 실패를 세 가지로 분류:

| 실패 유형 | 처방 |
|---|---|
| **컨텍스트 부족** | 정보 더 주기 (관련 파일·문서·예시) |
| **방향 오류** | 요구사항 다시 정의 |
| **구조적 충돌** | 코드 격리 + 가드레일 ("이 파일은 수정 X", "이 API 계약은 변경 X") |

저자가 A↔B 무한루프에 빠진 사례 — **"Must NOT Have"** 가드레일 한 줄로 루프를 끊었다.

### ⑥ 메모리 설계 

3일 연속으로 같은 작업하면서, 매일 아침 에이전트에게 "어제 JWT 구조 바꿨던 거 알지? 그 다음에…" 부터 시작하면 15분이 그냥 증발한다.

해법은 **MEMORY.md 자동 기록**. Claude Code의 hooks 같은 기능으로 세션 종료 시 결정·작업·이슈를 자동 추출해두면, 다음 세션 시작 시 그 파일 한 번 읽히면 **5초 안에 컨텍스트 복원**.

### ⑨ 감각 

{{< note2 >}}
80%가 범람하는 시대에 차별화는 나머지 20%에서 나온다
{{< /note2 >}}

마지막 ⑨번이 사실 가장 묵직하다. AI는 평균치 80%까지는 잘 만든다. 그런데 **"동작한다"** 와 **"훌륭하다"** 는 다른 차원이다.

    원문 예시: 검색 기능이 기술적으로 완벽한데 결과가 알파벳순으로 정렬돼 있어 쓰기 불편했다. 에이전트는 "검색 기능"을 만들었지만 "좋은 검색 경험"은 못 만들었다. 이 차이를 알아채는 것이 감각이다.

AI가 구현 장벽을 낮출수록, 설계·판단·감각이 **더 중요해진다**.

## Part 2. 실전 워크플로우 
> Research → Planning → Implementation

위 9가지가 "무엇을 갖춰야 하는가"라면, 이건 "오늘 당장 어떻게 일하면 되는가"에 가깝다.

핵심은 **모든 작업을 세 단계로 분리**하는 것. 이 분리가 없으면 에이전트는 research도 안 한 채 implementation으로 직진하고, planning은 머릿속에만 있고, 결국 검증 불가능한 결과물이 나온다.

### Step 1. Research — `research.md` 에 적게 한다

가장 흔한 실수는 채팅창 안에서 "이 코드베이스를 분석해줘 → 음 알았어 다음" 으로 끝내는 것. <br>
이러면 다음 step에서 그 분석이 **휘발된다**.

규칙은 단순하다.

{{< note2 >}}
**채팅 안에서 구두 요약으로 끝내지 말고, 반드시 발견한 내용은 `research.md` 에 적게 시킨다.**
{{< /note2 >}}

그리고 키워드 선택이 의외로 중요. 다음 단어들을 의도적으로 박아 넣는다:

- 이 폴더를 **"깊이"** 읽어
- 어떻게 동작하는지 **"깊이"** 이해해
- 모든 **"세부사항"** 을 파악해
- **"매우 상세한"** 보고서를 작성해

이 키워드들이 들어가면 에이전트의 출력 깊이가 눈에 띄게 달라진다. (Claude가 verbose 모드로 들어간다는 느낌)

### Step 2. Planning — `plan.md` 에 적게 하고, 주석을 단다

Research가 끝났으면 이번엔 구현 계획을 별도 파일에 적게 한다.

```
"코드 스니펫을 포함해 상세 plan.md를 작성해.
 소스 파일을 읽고 실제 코드베이스를 기반으로 작성해."
```

그리고 작성된 plan.md를 읽고 **직접 메모를 추가하는 단계**가 있다. <br>
`가정 수정`, `접근 방식 거부`, `제약 조건 추가`, `도메인 지식 전달` — 이걸 문서 안에서 직접 한다

```
plan.md
├─ 1. 인증 모듈 변경
│   └─ [내 메모] 기존 JWT 라이브러리 그대로 유지. 새로 추가하지 마.
├─ 2. DB 마이그레이션
│   └─ [내 메모] 이 부분 가정이 틀렸음. 우리 DB는 PostgreSQL 17.
└─ 3. ...
```

**"아직 구현하지 마"** 이 한 줄이 진짜 중요하다. 안 박으면 에이전트가 신나서 그대로 구현해버린다.

```
"문서에 메모를 추가했으니 메모를 반영하고 plan.md를 업데이트해.
 아직 구현하지 마."
```


### Step 3. Implementation — 멈추지 않게 잠금

계획이 충분히 다듬어졌으면 그제야 구현 시작. 

```
"plan.md 를 전부 구현해라.
 작업이나 단계를 완료하면 계획 문서에 완료로 표시해라.
 모든 작업과 단계가 완료될 때까지 멈추지 마라.
 any 나 unknown 타입을 쓰지 마라.
 지속적으로 typecheck 를 실행해서 새로운 문제를 만들지 마라."
```

마지막 두 줄은 **에이전트의 게으름 방지**용이다. 타입 검사를 우회하거나, 모호한 타입으로 도망가는 패턴을 미리 막는다.

## 가장 중요한 한 가지 — 잘못된 방향이면 통째 되돌리기

마지막으로, 9가지 스킬과 R·P·I 워크플로우 위에 깔리는 메타 원칙 하나.

{{< note4 >}}
**잘못된 방향으로 가고 있다면, 그 위에서 패치하지 말 것.**  
**`git` 변경을 통째로 되돌리고 범위를 재설정한다.**
{{< /note4 >}}

이게 진짜 어렵다. 인간 본능은 "여기까지 왔는데" 하면서 그 위에 또 한 겹 덧대고 싶다. <br> 
근데 잘못된 토대 위에 쌓인 코드는 **지수적으로 더 망가지지** 결코 더 좋아지지 않는다.

`git reset --hard HEAD` 하나로 30분 작업을 날리는 결단력이, 결과적으로 **하루를 살리는** 일이 의외로 많다.

## 정리

에이전틱 엔지니어링 시대에 갖춰야 할 9가지:
- 분해 · 컨텍스트 설계 · 완료 정의 · 실패 복구 · 관찰 가능성 · 메모리 설계 · 병렬 관리 · 추상화 계층 · 감각

그리고 그 9가지가 실제로 굴러가는 모양 — R·P·I:
- Research (`research.md`) → Planning (`plan.md` + 주석) → Implementation

마지막으로, 깊이 파묻혔어도 **방향이 틀렸으면 그냥 git으로 되돌릴 것**.
